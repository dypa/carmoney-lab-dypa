# plan_MILEAGE — пробег ≤ 400 000 км, иначе решение review

Задача MILEAGE (день 1): если пробег авто не больше 400 000 км — решение считается
как сейчас, по LTV; если пробег больше — решение `review`.

План составлен по формулировке задачи и прямому чтением кода: сверка с
`docs/setup/code_map.md` невозможна — файла в репозитории нет (задание 1.2.2 не
выполнено). Разведку всех упоминаний пробега (backend, frontend, db, tests, docs)
сделал @scout; ключевые файлы расчёта решения planner проверил сам. Артефакты
`intent_MILEAGE.md` и `spec_MILEAGE.md` тоже отсутствуют — в ДЗ.1 план свести со
спекой и дополнить.

Текущее поведение (проверено по коду): пробег участвует только в валидации ввода
(0…`max_mileage_km` = 500 000 км, иначе HTTP 422); в решении approve/review/reject
участвует только LTV. Правила «пробег > 400 000 → review» в коде нет.

Семантика решения, которую фиксирует план (LTV-ветки и их границы не меняются):

- `ltv > review_max` → `reject` — reject не смягчается пробегом;
- иначе `ltv >= approve_max` **или** `mileage > review_above_km` → `review`;
- иначе → `approve`.

Имя ключа `review_above_km` — выбор этого плана (семантика: «выше этого пробега —
review»), при ревью имя можно обсуждать, но менять только в этом плане.

## 3. Тесты

Границы по конвенции spec: 399999 / 400000 / 400001 и пустое значение. Все тесты
по AAA (`// Arrange` / `// Act` / `// Assert`), имя `test...` описывает поведение.

`tests/Unit/DecisionEngineTest.php` — движок; LTV фиксируем в approve-зоне (например 50.0):

## 4. Риски

1. **Существующая проверка `max_mileage_km` = 500 000 (rules.php:23, ApplicationValidator.php:44–45)** — главный риск. Если «в честь новой фичи» понизить валидационный предел до 400 000, диапазон 400 001–500 000 превратится из `review` в HTTP 422, и новое правило станет недостижимым. Валидатор и его лимит не менять; границы 400 001 / 500 000 / 500 001 фиксируются защитными тестами. По AGENTS.md пороги — зона риск-менеджмента: любое предложение поменять `max_mileage_km` — стоп и вопрос человеку.
2. **Приоритет reject** — семантика «reject не смягчается до review» — допущение планировщика. Если заказчик имеет в виду literal «пробег > 400 000 → review» поверх любого LTV-решения, придётся править логику `decide()` и два теста. Решается вопросом 1.
3. **Смена публичной сигнатуры `decide()`** — все вызовы обновляются в одном коммите: AssessmentService.php:33 и оба юнит-теста. Пропущенный аргумент даст `ArgumentCountError` → HTTP 500; `make lint` (php -l) это не ловит, ловят только тесты и ручной прогон обоих эндпоинтов.
4. **Дрейф существующих решений** — AssessmentServiceTest использует mileage 96 000, правило его не задевает: если три существующих теста решений покраснели, сломан LTV-путь, а не добавлено правило. Их ожидания не менять.
5. **`approved_limit` при пробегном review = 0** (AssessmentService.php:39) — получается автоматически, без отдельной правки; если заказчик ждёт иной лимит — это задача LOAN-12, не MILEAGE.
6. **Правило появится сразу в обоих эндпоинтах** — `POST /api/ltv` и `POST /api/applications` делят один AssessmentService. Это ожидаемое поведение, но ручная проверка (шаг 8) и e2e должны покрыть оба.
7. **Тексты ошибок 422** («Пробег от 0 до 500000 км») собираются через sprintf из `max_mileage_km` — не менять; фронтенд выводит их как есть (`frontend/app.js:37–41`).

Не входит (сознательно):

- правка `ApplicationValidator`, `max_mileage_km` и текстов ошибок валидации;
- фронтенд: атрибут `max` у поля пробега, клиентская валидация, стили (форма `novalidate`, все проверки на сервере; класс `decision--review` уже существует, фронт просто показывает `decision`);
- `db/schema.sql` (INT UNSIGNED вмещает диапазон, NOT NULL закрывает «пустой пробег» на уровне БД) и `db/seed.sql` (максимум 296 000, значения > 400 000 не нужны); миграций в проекте нет;
- расчёт `approved_limit` по `ltv_by_age` — задача LOAN-12;
- поле причины review в ответе API (меняет контракт) — вопрос 4;
- Feature/HTTP-тесты и e2e-сценарии (`tests/Feature/` сегодня пуст) — отдельная часть ДЗ.1;
- артефакты `intent/spec/grill_MILEAGE.md` — другие задания; план затем сверяется со спекой.
